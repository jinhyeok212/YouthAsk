# 이력서/자소서 문장 예시

## 이력서 한 줄 요약

온통청년 정책 API 기반 2,728건의 정책 데이터를 RAG 실험용 `documents.jsonl`로 표준화하고, SHA256 기반 manifest 검증 및 Runner 연동형 데이터 검증 자동화를 구현했습니다.

## 이력서 bullet 예시

- 온통청년 정책 데이터 2,728건을 RAG 검색 실험용 `documents.jsonl` 표준 스키마로 변환
- 정책 1건을 문서 1건으로 매핑하는 `one policy = one document` 구조 설계
- 후속 청킹/검색 기준 필드로 `retrieval_text`를 분리하여 문서 스키마 명확화
- `dataset_manifest.json`에 데이터 버전, 전처리 버전, 문서 수, SHA256을 기록해 데이터 재현성과 무결성 확보
- JSONL 파싱 오류, 필수 필드 누락, 빈 본문, 중복 ID, manifest count/hash 불일치를 자동 검증하는 `validate_documents(config)` 구현
- Experiment Runner에서 호출 가능한 데이터 검증 모듈을 구현하여 후속 청킹 단계로 잘못된 데이터가 넘어가지 않도록 fail-fast 구조 적용
- fixture 기반 테스트로 정상/비정상 데이터 케이스를 검증하고 `13 passed, 1 skipped` 결과 확보

## 자기소개서용 짧은 문단

RAG 프로젝트에서 데이터셋/전처리 담당으로 참여해 온통청년 정책 API 데이터를 검색 실험용 문서 데이터셋으로 표준화했습니다. 전체 정책 2,728건을 `documents.jsonl` 형식으로 변환하고, 후속 청킹과 검색에 사용할 `retrieval_text` 필드를 명확히 분리했습니다. 또한 `dataset_manifest.json`에 문서 수와 SHA256을 기록하고, Runner에서 `validate_documents(config)`로 데이터 무결성을 자동 검증하도록 구현했습니다. 이를 통해 후속 청킹, 임베딩, 검색 평가 단계가 신뢰할 수 있는 입력 데이터를 기반으로 실행될 수 있도록 만들었습니다.

## 자기소개서용 긴 문단

RAG 프로젝트에서 제가 맡은 역할은 온통청년 정책 데이터를 실험 가능한 형태로 정리하는 데이터셋/전처리 파트였습니다. 원본 API 데이터는 정책명, 지원 내용, 신청 방법, 제출 서류 등 여러 필드로 나뉘어 있었고, 바로 청킹이나 벡터 검색에 사용하기 어려웠습니다. 저는 전체 정책 2,728건을 대상으로 정책 1건을 문서 1건으로 매핑하는 `documents.jsonl` 스키마를 설계하고, 검색과 청킹에 사용할 `retrieval_text` 필드를 별도로 구성했습니다. 또한 데이터 품질을 사람이 매번 확인하지 않도록 `validate_documents(config)` 검증 모듈을 구현해 JSONL 파싱 오류, 필수 필드 누락, 빈 본문, 중복 ID, manifest 문서 수 불일치, SHA256 불일치 등을 자동으로 탐지하도록 했습니다. 이 과정에서 `dataset_manifest.json`에 데이터 버전과 파일 해시를 기록하여 실험 재현성을 확보했고, fixture 기반 테스트를 통해 정상/비정상 케이스를 검증했습니다. 결과적으로 후속 청킹, 임베딩, 검색 평가 담당자가 안정적으로 이어받을 수 있는 RAG 데이터 입력 계층을 구축했습니다.

## 면접에서 설명할 때 핵심 포인트

면접에서 이 경험을 설명할 때는 단순히 “데이터를 만들었다”가 아니라 다음 흐름으로 말하는 것이 좋다.

```text
문제:
원본 정책 API 데이터는 RAG 실험에 바로 쓸 수 있는 문서 구조가 아니었고, 품질 검증도 수동이었다.

해결:
전체 2,728건을 documents.jsonl로 표준화하고, retrieval_text를 청킹 기준 필드로 분리했다.

자동화:
validate_documents(config)를 구현해 Runner가 실행 전에 데이터 무결성을 자동 검증하도록 했다.

성과:
중복 ID, 빈 본문, 필수 필드 누락 0건을 확인했고, SHA256 기반 manifest 검증으로 재현성을 확보했다.
```

## 30초 답변 예시

제가 맡은 부분은 RAG 파이프라인의 데이터 입력 계층이었습니다. 온통청년 정책 API에서 수집한 2,728건의 정책 데이터를 `documents.jsonl` 표준 스키마로 변환했고, 청킹 기준 필드인 `retrieval_text`를 명확히 분리했습니다. 이후 Runner에서 `validate_documents(config)`를 호출하면 JSONL 파싱, 필수 필드, 중복 ID, 빈 본문, manifest count, SHA256까지 자동 검증되도록 구현했습니다. 이를 통해 후속 청킹과 임베딩 단계가 신뢰할 수 있는 데이터 위에서 실행되도록 만들었습니다.

## 1분 답변 예시

RAG 프로젝트에서 저는 데이터셋/전처리 담당으로 참여했습니다. 원본 온통청년 API 데이터는 여러 정책 필드가 흩어져 있어 바로 청킹하거나 검색 평가에 사용하기 어려웠습니다. 그래서 전체 정책 2,728건을 `one policy = one document` 구조의 `documents.jsonl`로 변환했고, 후속 담당자가 사용할 청킹 기준 필드를 `retrieval_text`로 정리했습니다. 또한 자동화 Runner에 연결될 수 있도록 `validate_documents(config)` 함수를 구현했습니다. 이 함수는 `documents.jsonl`의 존재 여부, JSONL 파싱, 필수 필드, 빈 값, 중복 ID, manifest 문서 수와 SHA256 일치 여부를 검증합니다. 검증 실패 시 예외를 발생시켜 잘못된 데이터가 후속 파이프라인으로 넘어가지 않게 했고, fixture 기반 테스트로 주요 실패 케이스를 검증했습니다. 결과적으로 데이터 생성뿐 아니라 재현성과 무결성을 갖춘 RAG 실험 입력 계층을 구축했습니다.
