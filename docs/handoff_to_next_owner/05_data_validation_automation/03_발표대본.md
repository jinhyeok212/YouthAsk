# 2번 데이터셋/전처리 담당 발표 대본

안녕하세요.

제가 맡은 2번 데이터셋/전처리 파트 진행 내용을 정리해서 말씀드리겠습니다.

이번 파트의 목표는 온통청년 전체 정책 데이터를 RAG 실험 자동화 파이프라인에서 사용할 수 있는 형태로 정리하고, Runner가 실행 전에 데이터 오류를 자동으로 검증할 수 있게 만드는 것이었습니다.

Runner 전체 흐름에서 제 파트는 config 검증 다음에 실행됩니다.

```text
Runner
→ config 검증
→ validate_documents(config)
→ contracts.validate_stage_result()
→ build_chunks(config, dataset_info)
```

즉, 제 파트는 후속 청킹 단계로 넘어가기 전에 `documents.jsonl`이 올바른지 확인하는 관문 역할을 합니다.

먼저 온통청년 전체 정책 2,728건을 RAG용 문서 형식으로 변환했습니다.

출력 위치는 다음입니다.

```text
C:\말똥가리\data\processed\ontong_youth_full_v1\
```

핵심 산출물은 세 개입니다.

```text
documents.jsonl
dataset_manifest.json
data_quality_report.csv
```

`documents.jsonl`은 정책 1개를 문서 1개로 보는 구조입니다.

각 문서에는 `document_id`, `title`, `source`, `url`, `content`, `retrieval_text`, `metadata`, `raw_record`가 들어갑니다.

여기서 후속 담당자가 가장 중요하게 봐야 하는 필드는 `retrieval_text`입니다.

청킹은 `content`가 아니라 `retrieval_text`를 기준으로 진행하면 됩니다.

데이터 검증 결과도 말씀드리겠습니다.

전체 문서 수는 2,728건이고, 중복 document_id는 0건입니다.

빈 document_id, 빈 title, 빈 retrieval_text, 빈 category도 모두 0건입니다.

필수 스키마 누락도 0건입니다.

문서 SHA256은 다음 값으로 기록했습니다.

```text
8688055b4553c79e9390e31831b5fefbef00925f24fb20af983a7ca552914a48
```

이 값은 `dataset_manifest.json`에도 들어가 있고, Runner 실행 시 실제 파일의 SHA256과 manifest에 기록된 SHA256이 일치하는지 확인합니다.

다음으로 자동화한 부분을 설명드리겠습니다.

기존에는 데이터를 사람이 직접 열어서 확인해야 했지만, 지금은 Runner가 다음 함수를 호출하면 자동으로 검증됩니다.

```python
from src.data.validate_documents import validate_documents

dataset_info = validate_documents(config)
```

이 함수는 `documents.jsonl` 존재 여부, JSONL 파싱, 필수 필드, 빈 값, 중복 ID, manifest 문서 수, SHA256, 데이터 버전까지 검증합니다.

검증이 성공하면 다음처럼 후속 단계에 넘길 정보를 반환합니다.

```json
{
  "document_path": "data/processed/ontong_youth_full_v1/documents.jsonl",
  "manifest_path": "data/processed/ontong_youth_full_v1/dataset_manifest.json",
  "document_count": 2728,
  "sha256": "8688055b4553c79e9390e31831b5fefbef00925f24fb20af983a7ca552914a48"
}
```

이 반환값은 3번 청킹 담당자가 `build_chunks(config, dataset_info)`에서 이어받게 됩니다.

검증 실패 시에는 조용히 넘어가지 않고 예외를 발생시킵니다.

예를 들어 깨진 JSON 줄, 필수 필드 누락, 빈 본문, 중복 document_id, manifest count 불일치, SHA256 불일치가 있으면 해당 단계에서 멈추게 됩니다.

테스트도 작성했습니다.

실제 전체 데이터를 쓰지 않고 임시 JSONL과 manifest를 만들어 fixture 기반으로 테스트했습니다.

테스트한 케이스는 정상 문서, 깨진 JSON, dict가 아닌 레코드, 필수 필드 누락, 빈 값, 중복 ID, version 불일치, manifest count 불일치, hash 불일치입니다.

테스트 결과는 다음과 같습니다.

```text
13 passed, 1 skipped
```

여기서 skip 하나는 PM의 `contracts.py`가 아직 현재 작업공간에 없어서 contract 연동 테스트만 건너뛴 것입니다. PM 모듈이 들어오면 그 테스트도 자동으로 실행할 수 있습니다.

제가 추가하거나 수정한 주요 파일은 다음입니다.

```text
scripts/build_ontong_youth_full_documents.py
src/data/validate_documents.py
src/data/build_dataset_manifest.py
tests/test_document_validation.py
tests/test_core.py
```

마지막으로 다음 담당자에게 넘길 내용을 말씀드리겠습니다.

3번 청킹 담당자는 다음 파일을 입력으로 사용하면 됩니다.

```text
C:\말똥가리\data\processed\ontong_youth_full_v1\documents.jsonl
```

청킹 대상 필드는 `retrieval_text`입니다.

3번 담당자가 다음으로 만들어야 할 파일은 다음입니다.

```text
C:\말똥가리\data\processed\ontong_youth_full_v1\chunks.jsonl
C:\말똥가리\data\processed\ontong_youth_full_v1\chunk_manifest.json
```

정리하면, 2번 데이터셋/전처리 담당 업무는 완료된 상태입니다.

전체 온통청년 2,728건 문서화가 끝났고, `validate_documents(config)`도 Runner에서 바로 호출 가능한 상태입니다.

다음 단계는 3번 담당자가 `retrieval_text` 기준으로 `chunks.jsonl`을 생성하는 것입니다.

이상입니다.
